# 标擎 BidPilot v0.8.0 零基础交接手册

更新时间：2026-08-02

适用版本：v0.8.0
代码仓库：<https://github.com/gitchw/bidpilot>

这份手册写给第一次接触 BidPilot、Python 和本地 Web 服务的接手人。目标不是解释每一行代码，而是让你能安全地完成：安装、启动、检查、配置、日常值守、备份、升级和排障。

## 1. 先用一句话理解项目

BidPilot 是一个本地运行的招投标情报工作台：它把自然语言查询解析成结构化意图，从多个公开来源检索公告，生成可追溯的证据与 Word 报告，并通过长期订阅和可靠投递队列把结果发到一个或多个渠道。

默认网页地址是：<http://127.0.0.1:8000>。

`127.0.0.1` 表示“当前这台电脑”，`8000` 是默认端口。默认状态下，其他电脑和手机不能访问，更不是一个已经部署到公网的网站。

## 2. 接手后的第一小时

按顺序完成下面八件事，不要一上来修改代码或删除文件。

1. 确认项目目录。下文所有命令都要在包含 `pyproject.toml`、`bootstrap.py` 和 `bidpilot/` 的项目根目录执行。
2. 运行 `python --version`，确认 Python 版本不低于 3.11。
3. 运行 `git status`，确认当前有没有尚未提交的修改。不要覆盖不明来源的改动。
4. 如果还没有 `.venv`，运行 `python bootstrap.py --dev` 安装项目与开发依赖。
5. 按第 4 节启动服务，打开 <http://127.0.0.1:8000>。
6. 按第 5 节检查状态，确认 Web 服务和 worker 都在线。
7. 打开“配置中心”，只检查“已配置/未配置”状态，不要随意清除敏感字段。
8. 在改动任何数据或配置前，先按第 11 节完成一次完整备份。

## 3. 目录地图：什么能改，什么不能丢

| 路径 | 作用 | 交接要求 |
|---|---|---|
| `bidpilot/` | 后端、检索、意图、worker、投递和网页静态资源 | 产品代码，修改后必须跑测试 |
| `tests/` | 自动化测试 | 不要为了“让测试通过”而删除失败用例 |
| `docs/` | 用户、配置、渠道、API 与交接文档 | 功能变化后同步更新 |
| `tools/` | 文档、截图等构建工具 | 不是运行服务的必需进程 |
| `data/bidpilot.db` | SQLite 数据库，保存订阅、运行、结果、机会和配置 | 重要业务数据，不要手工编辑或提交 Git |
| `data/secrets/` | 本机加密密钥、停止令牌和可选来源授权 | 必须和数据库一起备份，绝不能公开 |
| `outputs/reports/` | 运行生成的 Word 报告 | 按业务要求备份或归档 |
| `outputs/manuals/` | 正式操作说明书及配图 | 发布版本时更新 |
| `pyproject.toml` | 版本、依赖、测试与格式化配置 | 升级版本时重点核对 |
| `compose.yaml` | Docker Web/worker 部署 | 与原生 Python 生命周期不要混用 |

最重要的规则：`data/bidpilot.db` 与 `data/secrets/` 下的全部 `.key` 文件必须来自同一次备份。只保留数据库、漏掉密钥，会导致已保存的模型、渠道或来源授权无法解密。

## 4. 安装与启动

### 4.1 推荐方式：原生 Python

第一次安装或依赖变化后运行：

```text
python bootstrap.py --dev
```

Windows 启动：

```text
.venv\Scripts\python.exe -m bidpilot serve
```

macOS / Linux 启动：

```text
.venv/bin/python -m bidpilot serve
```

启动后不要关闭这个终端。看到服务地址后，在浏览器打开：

```text
http://127.0.0.1:8000
```

API 交互文档位于：

```text
http://127.0.0.1:8000/docs
```

### 4.2 Docker Compose

只有已安装 Docker Desktop 或 Docker Engine + Compose 时才使用：

```text
docker compose up -d --build
docker compose ps
docker compose logs -f worker
```

Compose 容器内固定监听 8000，宿主机默认映射到 `127.0.0.1:8000`。Docker 的端口映射由根目录 `.env` 中的 `BIDPILOT_PORT` 控制；网页配置中心的“服务端口”只控制原生 Python 服务，不会改写 Compose。

## 5. 状态、停止与重启

### 5.1 查看状态

Windows：

```text
.venv\Scripts\python.exe -m bidpilot status
```

macOS / Linux：

```text
.venv/bin/python -m bidpilot status
```

重点看：版本、监听地址、数据库路径、报告目录、worker 是否在线、是否有到期任务。

### 5.2 优雅停止

如果启动终端还在，可在该窗口按 `Ctrl+C`。也可以在另一个终端运行：

```text
# Windows
.venv\Scripts\python.exe -m bidpilot stop --wait-seconds 20

# macOS / Linux
.venv/bin/python -m bidpilot stop --wait-seconds 20
```

看到“服务已优雅停止”才算结束。停止不会删除数据库、订阅、机会或报告。不要直接结束未知 Python 进程，也不要删除 `data/secrets/control.token` 来假装停止成功。

### 5.3 重启

```text
# Windows
.venv\Scripts\python.exe -m bidpilot restart

# macOS / Linux
.venv/bin/python -m bidpilot restart
```

独立运行的 `bidpilot worker` 是另一个前台进程，需要在它自己的终端按 `Ctrl+C`；普通 `bidpilot stop` 只负责可管理的 Web 服务及其内嵌 worker。

### 5.4 Docker 生命周期

```text
docker compose stop
docker compose start
docker compose restart
docker compose down
```

`docker compose down` 默认保留命名卷。不要随手加 `-v`，否则数据库和报告卷可能被永久删除。Docker 部署不要用宿主机 `.venv` 的 `bidpilot stop/restart` 管理。

## 6. 网页配置中心

日常配置优先在网页“配置中心”完成，不需要手改配置文件。页面按卡片独立保存，并标出“立即生效”或“重启后生效”。

配置时遵守下面的顺序：

1. 修改一张卡片。
2. 点击“保存本卡修改”。
3. 等待成功提示。
4. 如果该卡有测试按钮，再点击测试；渠道测试会真实外发，页面会二次确认。
5. 网络范围、LAN 策略、可信网段、管理员令牌和端口发生变化后，按页面提示重启。

敏感字段不会回显原文。“留空”通常表示保留原值；要删除必须勾选明确的“清除”选项。不要因为页面显示星号或“已配置”，就反复粘贴或清除密钥。

完整的 62 个字段解释见 [配置中心指南](CONFIGURATION_GUIDE.md)。

## 7. LLM：为什么接入、怎样配置、失败会怎样

### 7.1 它在产品中的作用

BidPilot 不是把全部判断交给模型。核心流程是：

```text
本地规则基线 → 低置信/缺失/冲突字段交给 LLM → 严格 JSON → 本地逐字段校验 → 用户确认快照 → 执行
```

模型还可辅助检索规划、二轮补搜、主题边界复核、逐公告摘要、情报简报、企业适配复核和证据追问。日期、地域编码、公告类型、来源能力和证据引用仍由本地代码约束。

模型不可用、超时、返回非法 JSON 或提议不合规时，系统回退到规则和本地证据，不会把模型故障伪装成模型结论。

### 7.2 网页配置步骤

在“配置中心 → AI 与意图”填写：

- OpenAI-compatible API 基础地址；
- 模型名称；
- API Key；
- 超时；
- 意图辅助、检索规划、摘要、简报和企业适配模式。

先保存，再点“测试模型连接”。测试成功只说明地址、密钥和模型当前可调用；真实任务仍可能受超时、额度、限流或模型格式遵循能力影响。

### 7.3 隐私提醒

使用云端模型时，自然语言查询和相应功能所需的有限证据文本会离开本机。系统不会把模型 API Key、Webhook、Cookie、完整数据库、投递账本或机会私密字段作为模型上下文发送。处理敏感项目时，应先确认模型服务商的隐私政策，必要时把相关 AI 模式设为 `off` 或使用可信的本地兼容服务。

## 8. 检索、来源和合规边界

“来源中心”显示每个来源的健康、覆盖范围和授权状态。看到“部分覆盖”不是成功，也不代表整个互联网已经检索完毕；它说明该来源受公开范围、分页、授权、频率或结构变化限制。

平台授权必须由用户本人在可见浏览器中完成。授权窗口会出现在运行 BidPilot 的服务电脑上，局域网手机只能发起、完成、测试或清除操作，不能把登录窗口搬到手机上。

BidPilot 不自动填写账号密码，不破解验证码，不绕过 WAF、付费墙、角色权限、robots 规则或频率限制。来源没有授权或没有公开详情时，应如实显示覆盖缺口，并保留原站入口供用户处理。

## 9. 长期任务和多个投递渠道

长期订阅写入 SQLite，由 worker 定时领取和执行；浏览器只负责管理，关闭网页不会终止订阅。关闭服务电脑、停止 worker 或删除数据库才会使任务停止运行或丢失。

当前可用交付目标包括：

- 本地报告；
- 飞书群机器人；
- 飞书应用；
- SMTP 邮件；
- 钉钉群机器人；
- 企业微信群机器人；
- 通用 Webhook；
- Telegram Bot；
- Slack Incoming Webhook。

一个查询或订阅可以同时选择多个已就绪目标。系统先把每个目标写入 Outbox，再逐目标发送、确认和重试；一个渠道失败不会抹掉其他渠道的成功。临时失败会退避重试，多次失败进入死信，修复配置后可只重排该失败目标。

不同平台能力不同：Slack Incoming Webhook 发送消息和安全报告链接，不冒充文件上传接口；Telegram 的 Word 文件超过平台限制时需要配置安全的报告地址。完整矩阵和死信处理见 [投递渠道与可靠性指南](DELIVERY_CHANNELS.md)。

## 10. 局域网访问

默认保持“仅本机”，即 `127.0.0.1:8000`。需要手机或其他电脑访问时：

1. 打开“配置中心 → 长期任务与局域网”。
2. 把访问范围改为“局域网设备”。
3. 优先选择“管理员令牌保护”；只有同网设备全部可信时才使用“可信局域网免令牌”。
4. 保持端口 8000，除非它确实被占用。
5. 保存并重启原生服务。
6. 在其他设备打开 `http://服务电脑的局域网IP:8000`。

LAN 使用普通 HTTP，不提供传输加密，也不是公网部署方案。不要在路由器做端口映射，不要把服务直接暴露到公网。确需公网访问时，应由专业运维在反向代理层增加 HTTPS、登录和角色权限、CSRF/来源校验、限流和审计。

## 11. 数据与备份

### 11.1 原生 Python 的稳妥备份

1. 使用第 5 节的命令优雅停服。
2. 确认 `status` 显示服务未运行。
3. 整体复制 `data/`，不要只复制 `data/bidpilot.db`。
4. 如需保留历史 Word，同时复制 `outputs/reports/`。
5. 备份目录使用日期命名，并保存在受保护的位置。

恢复时也要先停服，再把同一次备份的整个 `data/` 放回项目根目录；如需历史报告，再恢复 `outputs/reports/`。恢复后先运行 `status`，再启动并检查配置中心的“已配置”状态。

### 11.2 Docker 数据

Compose 把 `/app/data` 和 `/app/outputs/reports` 放在命名卷中。升级或重建容器前先按组织的 Docker 卷备份流程导出这两个卷。`docker compose down` 不等于备份；`docker compose down -v` 会删除卷，除非已经验证备份且明确要清空，否则禁止执行。

### 11.3 绝不能公开的内容

- `.env`；
- `data/` 和数据库；
- `data/secrets/` 下的密钥、控制令牌和授权会话；
- API Key、密码、完整 Webhook、Cookie；
- 未脱敏的商业敏感查询、报告和日志。

## 12. 常见故障速查

| 现象 | 先做什么 | 仍未解决时 |
|---|---|---|
| 网页打不开 | 运行 `status`，核对真实地址和端口 | 看启动终端错误；确认端口未被占用 |
| 地址变成 8012 | 检查配置中心保存的原生端口，或 Compose 的 `BIDPILOT_PORT` | 按对应部署方式重启，不要混用两套端口 |
| 无法停止 | 使用启动时同一个 `.venv` 解释器运行 `stop --wait-seconds 20` | 核对 `status` 显示的控制目录；Docker 用 Compose 停止 |
| worker 离线 | 普通本机确认 `serve` 终端仍开；Docker 运行 `docker compose ps` | 查看 worker 日志和数据库路径是否一致 |
| 订阅“没有下文” | 看订阅下次运行时间、worker 心跳和本轮运行段 | 看 Outbox 是否等待重试或进入死信 |
| 地域/主题解析错 | 先看“解析意图”的规则、LLM 和合并轨迹 | 修改原句并重新确认，不要绕过意图快照 |
| 模型测试失败 | 核对基础地址、模型名、密钥、网络和额度 | 暂时关闭 AI 模式，任务会回退到本地规则 |
| 检索结果少或为 0 | 看来源中心的健康、授权和覆盖说明 | 放宽日期/主题，检查来源原站，保留覆盖缺口 |
| 一个渠道失败 | 在 Outbox 查看该目标回执 | 修复该渠道后只重排失败目标 |
| 重启后敏感配置不可用 | 检查数据库和 `data/secrets/*.key` 是否来自同一次备份 | 无法恢复密钥时，显式清除并重新填写相关凭据 |

更完整的逐步决策树见 [零基础操作说明书](BEGINNER_MANUAL.md) 第 17 章。

## 13. 安全升级流程

### 13.1 原生 Python

1. 运行 `git status`，保存或提交当前合法改动；不要直接覆盖脏工作树。
2. 按第 11 节备份完整 `data/` 和需要的报告。
3. 优雅停服。
4. 从受信任仓库获取新版本，并核对版本说明和标签。
5. 运行 `python bootstrap.py --dev` 更新虚拟环境依赖。
6. 运行第 14 节的质量检查。
7. 启动服务，运行 `status`，打开首页、配置中心、来源中心和订阅中心完成冒烟检查。
8. 确认旧订阅、机会、配置、运行历史和报告仍可见后，才结束升级窗口。

### 13.2 Docker Compose

1. 先备份两个命名卷。
2. 获取新代码后运行 `docker compose up -d --build --force-recreate`。
3. 运行 `docker compose ps`，等待 Web 健康且 worker 在线。
4. 运行 `docker compose logs --tail 200 web worker` 检查迁移和启动错误。
5. 完成与原生方式相同的网页冒烟检查。

如果升级后出现严重问题，停止新版本，恢复“代码版本 + 同一次数据备份”，不要把新数据库与旧密钥或旧数据库与新密钥拼接使用。

## 14. 修改代码后的最低质量门槛

Windows：

```text
node --check bidpilot/static/app.js
.venv\Scripts\python.exe -m ruff format bidpilot tests tools
.venv\Scripts\python.exe -m ruff check bidpilot tests tools
.venv\Scripts\python.exe -m pytest -p no:cacheprovider
```

macOS / Linux：

```text
node --check bidpilot/static/app.js
.venv/bin/python -m ruff format bidpilot tests tools
.venv/bin/python -m ruff check bidpilot tests tools
.venv/bin/python -m pytest -p no:cacheprovider
```

还应检查：API 文档能打开、配置中心字段均有中文说明、浏览器控制台无错误、移动端无横向溢出、长期任务能产生运行段与 Outbox、日志和报错没有泄漏密钥。

## 15. 交接完成标准

只有以下项目全部打勾，才算完成一次可靠交接：

- [ ] 接手人能独立找到项目目录并解释 8000 端口是什么；
- [ ] 能在 Windows 或 macOS/Linux 上启动、查看状态、停止和重启；
- [ ] 知道原生 Python 与 Docker 生命周期不能混用；
- [ ] 能在网页配置模型和至少一个投递渠道，并理解测试会真实外发；
- [ ] 知道长期任务依赖 worker，而不是浏览器标签页；
- [ ] 能完整备份和恢复 `data/` 与报告；
- [ ] 知道 LAN 不是公网方案，不能绕过登录、验证码、WAF 或付费权限；
- [ ] 知道哪些文件和内容绝不能提交、截图或发送给他人；
- [ ] 能运行测试，并在失败时保留证据而不是删除用例；
- [ ] 知道从 [零基础操作说明书](BEGINNER_MANUAL.md)、[配置中心指南](CONFIGURATION_GUIDE.md)、[API 参考](API_REFERENCE.md) 和 [投递渠道指南](DELIVERY_CHANNELS.md) 继续查阅细节。

## 16. 请求帮助时应提供什么

可以提供：

- 操作系统和 Python 版本；
- BidPilot 版本；
- 使用原生 Python 还是 Docker；
- `status` 的脱敏输出；
- 失败时间、点击步骤和错误码；
- 来源名、渠道名、任务/运行/投递编号；
- 已去除密钥、Cookie、完整 URL 查询参数和商业敏感原句的日志片段。

绝对不要提供 API Key、密码、完整 Webhook、Cookie、`.env`、`data/`、数据库、任何 `.key` 文件或 `control.token`。
