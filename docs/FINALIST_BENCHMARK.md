## 1. 先说明事实边界

截图只展示了三支队伍的一行评语，没有作品全文、演示视频、代码、实测数据或最终名次。因此，本文可以确认的是“评审文字强调了什么”，不能据此断言其他作品已经完整实现某项功能，也不能推断其架构、数据规模、合规状态或性能优劣。

截图中可以直接读出的信息如下：

| 作品 | 截图评语可确认的关注点 | 不能从截图推出的结论 |
|---|---|---|
| TenderTrace | 方案明确了业务对象和执行动作，能够贴近企业采购实际流程；完成度高，并设计了较完整的评价体系 | 不能确认其实际接入来源、线上稳定性、数据准确率或具体评价算法 |
| 讯标雷达 | 评语提及国内招投标平台 API 定位、免费登录态、监控采集、定时推送及 Web/应用实践；“核心内容绑定原文片段、来源和附件，无证据不补写”被视为主要亮点 | 不能确认其登录实现是否可长期运行、可访问哪些平台、是否覆盖付费内容、接口调用量或生产部署方式 |
| 标擎 BidPilot | 评审认可“可信情报工作流”的命题理解、10 个数据来源以及面向长期运行的真实工程建设，认为完成度高 | 不能仅凭本行评语宣称在业务闭环、评价体系或交付形态上全面领先 |

后续材料必须继续区分三种表述：

- **已验证能力**：有代码、测试、真实运行结果、界面或运维记录支撑，可用“已实现”“已验证”。
- **试点目标**：尚待客户环境验证的业务指标，必须写明“4 周试点目标”或“建议验收阈值”。
- **后续候选能力**：尚未实现的设想，只能写入路线图，不能出现在“现有功能”或 Demo 口播中。

## 2. 从评审反馈提炼出的通用胜出规律

### 2.1 从“功能列表”升级为“业务对象 × 执行动作 × 结果责任”

TenderTrace 的评语说明，评审关心的不是抽象 Agent 概念，而是系统究竟操作什么对象、执行什么动作、把谁的工作推进到哪一步。BidPilot 已有完整工程能力，但在比赛表达上应统一为下面这条主线：

| 业务对象 | 关键动作 | 可见结果 | 责任边界 |
|---|---|---|---|
| 检索任务 | 解析、确认、执行、补搜 | 查询口径、来源漏斗、固定证据集 | 模型建议检索词，本地规则决定硬过滤 |
| 来源与授权 | 登录、验证、复用、失效、清除 | 授权状态、最近验证、失败原因 | 仅复用本人合法免费账号权限，不突破付费或角色权限 |
| 标讯证据 | 抓取、清洗、提取、去重、聚类 | 原文、来源、附件、证据片段、项目时间线 | 无证据不生成事实，摘要不能替代原文 |
| 企业机会 | 适配、分级、反馈、跟进、归档 | 建议、风险、下一步、负责人和待办 | 分数是辅助判断，不承诺中标 |
| 采购单位 | 聚合、观察、创建监控 | 活跃主题、生命周期、近期证据 | 只基于本地已采集真实公告形成洞察 |
| 订阅与交付 | 调度、增量识别、投递、重试 | 仅新增、逐目标状态、死信与报告 | 来源覆盖与渠道送达分别披露，不伪装成功 |
| 审计记录 | 固化、追溯、复核 | 运行口径、版本、来源诊断、测试证据 | 登录凭据、Cookie、Token 不进入报告和代码仓库 |

比赛材料中每介绍一个模块，都应回答四个问题：对象是什么、系统做了什么、用户得到什么、失败时如何披露。这样能把“10 个来源”从数量优势转成企业采购工作流优势。

### 2.2 把“证据优先”从口号变成可点击的交互契约

讯标雷达评语再次验证了证据绑定的竞争力。BidPilot 不宜只写“可追溯”，而应在页面、Word、Demo 和验收表中反复呈现同一套契约：

1. 每条结构化事实必须能回到固定证据编号、原文链接或原始字段。
2. 核心内容同时展示来源、证据片段和附件；原站没有附件时明确标记“未发现附件”，不能补造。
3. 模型只能在给定证据内摘要、复核或选取逐字片段，不能生成公告、URL、采购人、日期和项目编号。
4. 来源失败、需要登录、只覆盖首屏或字段缺失时，结果页与 Word 都保留缺口，不把“未知”写成“没有”。
5. 任何评估结论都应有分数账本、命中依据、风险和下一步；用户可以回原文复核。

这套契约是可以现场验证的产品行为，不需要引用竞品，也不依赖夸大的准确率数字。

### 2.3 把登录态能力讲成可运维的服务器能力

用户本人免费账号的合法登录持久化，不等于绕过付费墙。比赛材料应明确把“权限边界”和“服务器可运维性”同时讲清：

千里马官方《会员注册须知》第 6-7 条同时禁止非人为连续、频繁查询和机器化大批量获取。因此，“账号免费可见”不能自动推导出“允许无人值守定时抓取”；在没有原站书面授权时，会员增强必须保持为用户主动、低频、有界操作，长期订阅继续使用公开来源。

- 首次登录由用户本人在可见浏览器中完成，系统不自动填写密码、不破解验证码。
- 登录状态保存在部署服务器专用的持久浏览器配置中，不导出 Cookie、不通过普通 HTTP 客户端重放。
- 验证通过后，Linux 后台可由同一浏览器 profile 执行受限的即时列表检索；每次运行仍受账号实际可见范围、跨进程互斥、页数、频率和每日预算约束。只有取得原站书面授权或官方 API 权利并登记记录编号后，才可启用单独审计的会员监控策略。
- 页面应展示“未登录 / 待验证 / 已验证 / 已失效 / 验证失败”等真实状态，以及最近验证时间、最近使用结果和重新登录入口。
- 账号退出、平台要求重新验证、DOM/WAF 变化或服务器迁移时，系统应显式降级到公开来源并提示管理员，而不是把缓存结果伪装成在线成功。
- 持久配置、数据库和密钥纳入停服备份与最小权限管理，但不得进入 Git、源码 ZIP、截图或比赛附件。

这里的产品卖点不是“绕过免费登录”，而是“在原站许可的账号权限内，把一次人工登录变成可验证、可失效、可清除、可审计的服务器会话生命周期”。

### 2.4 用评价体系证明“真实工程”服务于业务结果

评审对 TenderTrace “完整评价体系”的肯定，提示 BidPilot 需要在方案中增加独立的验收矩阵。建议采用四层指标，不将试点目标写成既有成绩：

| 评价层 | 建议指标 | 计算或核验方式 | 证据载体 |
|---|---|---|---|
| 来源可用性 | 来源成功率、授权状态准确率、覆盖缺口披露率 | 按运行记录统计成功/部分/失败；人工抽查状态与真实页面一致 | 来源中心、运行诊断、审计日志 |
| 情报可信度 | 字段可追溯率、附件关联率、重复合并可解释率、无证据补写数 | 随机抽样逐条回到原文；统计无来源事实，目标必须为 0 | 固定证据、Word、原文与附件 |
| 检索质量 | 主题有效率、硬条件误保留率、跨站重复率、零结果可解释率 | 预先冻结样本题和人工金标准，双人复核分歧 | 样本集、判定表、结果漏斗 |
| 工程可靠性 | 跨平台通过率、任务成功率、单源故障隔离、投递可追踪率、恢复时间 | CI、故障注入、systemd/容器记录、逐目标账本 | 测试报告、日志、部署审计 |
| 业务采用 | 首次检索耗时、人工筛选时间、有效机会确认率、跟进动作完成率 | 4 周试点前后同口径对照，不以演示数据代替客户数据 | 基线表、试点周报、用户确认单 |

建议比赛提交只承诺“评价方法与可验证证据已设计”。效率、覆盖率和机会转化等数字必须等真实客户试点后再填；评委现场可以验证的是可追溯率、无证据补写、故障披露和流程闭环。

## 3. BidPilot 的差距判断与优先级

### P0：比赛提交前必须强化

| 差距 | 修改方向 | 可核验验收标准 |
|---|---|---|
| 现有材料容易从技术架构开始，企业采购角色不够前置 | 首屏先写角色、痛点、对象、动作和产出，再讲架构 | 方案前 3 页内出现“业务对象—执行动作—用户结果”闭环；评委无需看架构图即可复述用途 |
| 评价体系分散在测试、审计和试点目标中 | 新增一页五层评价矩阵，并标注现状/试点目标/取证方式 | 每个指标都有口径、证据、责任人和事实状态；不存在把目标写成实绩的数字 |
| 千里马登录持久化容易被误读为本机演示或权限绕过 | 用“服务器会话生命周期”图解释首次登录、验证、复用、失效、清除、降级 | Demo 中可显示真实状态及一次授权内查询；不展示凭据、不访问付费详情；失效状态有明确提示 |
| 证据优先表达虽强，但视觉锚点不够统一 | 所有演示结果固定突出 E 编号、来源、原文、附件和缺口 | Demo 随机点开一条能回到原文；缺字段不补写；Word 与页面的核心字段一致 |
| 10 个来源容易被理解为“数量堆叠” | 把来源按业务能力分组，展示支持关键词、详情、附件、地域和授权边界 | 来源中心能看到每个来源真实模式及本轮扫描/候选/保留，不以来源卡片名称冒充覆盖 |

### P1：建议在下一轮产品迭代完成

| 能力 | 为什么重要 | 建议验收标准 |
|---|---|---|
| 授权会话运维面板 | 让 Linux 服务端的登录持久化可观察、可恢复 | 显示状态、最近验证、最近成功检索、配置目录健康、重新登录/清除入口；不回显 Cookie |
| 订阅覆盖体检 | 长期任务最怕来源悄然失效 | 每条订阅显示近 7 日来源健康与授权缺口；覆盖退化产生独立告警，不与“0 条新增”混淆 |
| 变化指纹与事件提醒 | 企业关心截止时间、金额、附件和阶段变化，而不只是新公告 | 同项目变更能列出确定性字段 diff，并链接变更前后证据；模型只能改写已识别 diff |
| 试点评价台账 | 让“高完成度”变成可交付验收 | 可导出运行样本、人工判定、系统判定、分歧原因和修复记录；指标可重复计算 |
| 角色化工作台 | 让采购情报进入售前/销售/审计协同 | 情报员可筛选、业务人员可跟进、审计角色可只读复核；在未实现权限模型前不得宣称已有 RBAC |

### P2：路线图候选，不应包装为现有能力

- 采购日历与截止时间日程订阅。
- 订阅沙盘：保存前用本地历史证据估算命中量与噪声。
- 机会协同 SLA、负责人负载和跟进复盘。
- 经过采购单位确认的供应商画像或产品目录联动。
- 移动端原生应用。当前 Web 可响应式使用时，应写“Web/移动浏览器”，不能写成已有 App。

## 4. 对 40 强参赛方案的具体增强文字

以下文字可按版面压缩后写入方案，但在落版前仍应与真实界面、测试和版本号逐项核对。

### 4.1 建议替换项目一句话定义

> 标擎 BidPilot 不是公告聚合页，而是一套面向企业采购情报人员、销售与审计复核者的证据驱动工作流：它把自然语言需求编译成可确认的检索或订阅任务，从真实来源取得并固化证据，完成硬条件筛选、跨站去重、企业适配和机会跟进，再将仅新增结果以可追溯 Word 与消息送达；任何来源失败、授权缺口和字段未知都会被保留，而不是由模型补写。

### 4.2 建议新增“业务闭环”页

标题建议：**从一句需求到一次可追责的跟进动作**

正文建议：

> 情报人员创建并确认检索口径；系统执行有界多源检索，形成带 E 编号的固定证据集；业务人员依据适配分、风险与原文决定参与、观察或暂不投入；值得跟进的项目进入机会工作台，采购单位进入买方雷达；订阅 worker 只推送新增或真实变化；审计人员可从报告和运行记录复核来源、附件、规则与送达状态。单个来源失败不会拖垮整轮，但会在结果和报告中留下覆盖缺口。

这页应配一张对象流图，而不是罗列功能图标：

`需求 → 检索任务 → 固定证据 → 机会判断 → 跟进/买方监控 → 增量交付 → 审计复核`

### 4.3 建议新增“评价与验收”页

标题建议：**不是自报准确率，而是让评委现场复核**

正文建议：

> BidPilot 将验收拆为来源可用性、情报可信度、检索质量、工程可靠性和业务采用五层。现场可随机选择结果回到原文和附件，检查无证据补写、硬条件过滤、重复合并、来源故障披露和逐目标送达；业务效率与机会转化只作为 4 周试点目标，在客户真实基线上做前后对照，不以演示数据冒充实绩。

### 4.4 建议强化“千里马免费登录态”页

标题建议：**合法权限内的服务器会话生命周期**

正文建议：

> 用户本人首次在可见浏览器完成免费账号登录，BidPilot 在部署服务器保留专用持久浏览器 profile 并执行真实验证。验证通过后，Linux 后台可以在账号原本可见范围内复用该 profile 执行受页数、结果数、冷却和每日预算约束的即时列表检索；系统不导出或 HTTP 重放 Cookie，不破解验证码，不访问付费详情。会话过期或平台要求复验时，来源状态会降级并提示重新登录，不用旧缓存伪装成功。

应配状态机：

`未登录 → 用户可见登录 → 待验证 → 已验证 → 后台受限复用 → 失效/复验 → 重新登录或清除`

### 4.5 建议强化差异化页

不要用“来源更多”“AI 更强”作为唯一差异。建议改成三层：

1. **流程闭环**：从检索到机会、买方、订阅、交付和审计，而非搜完即止。
2. **证据闭环**：结构化字段、摘要、判断和追问都受固定证据约束；无证据不补写。
3. **运行闭环**：来源隔离、授权失效、后台 worker、逐目标投递、跨平台测试和 Linux 运维可被复核。

## 5. 对详细设计文档的具体增强文字

### 5.1 新增“领域对象与责任边界”章节

建议列出 `IntentSnapshot`、`Run`、`SourceAttempt`、`TenderRecord`、`EvidenceSnapshot`、`Opportunity`、`BuyerMonitor`、`Subscription`、`DeliveryTarget`、`OutboxItem`、`SourceAuthorization` 等真实对象。对每个对象至少说明：主键/版本、创建者、状态机、不可变字段、关联证据、删除或归档语义。对象名称需以当前代码模型为准，不存在的类名不得为了文档整齐而虚构。

推荐章节开头文字：

> 系统以运行快照而不是聊天上下文作为审计边界。查询口径确认后生成不可任意改写的意图快照；每次来源调用形成独立尝试与诊断；入选公告固化为本轮证据快照；后续机会、买方和交付对象引用该证据，不允许浏览器直接提交未经证据库验证的项目事实。

### 5.2 新增“授权来源状态机与服务器拓扑”章节

至少描述：

- 首次可见登录发生在运行 BidPilot 的主机，不在远端手机浏览器中转账号凭据。
- 持久浏览器目录、数据库状态与密钥的所有权、权限、备份、迁移和清除。
- 已验证配置在 Linux systemd worker 中的复用方式及互斥，避免同一 profile 并发损坏。
- 超时、退出登录、验证码、WAF、页面结构变化和权限不足的分类诊断。
- 公开源降级策略、结果覆盖标记和审计字段。
- 容器部署若不含 Chromium，应明确不支持该模式，不把 Compose 与 systemd 能力混写。

推荐安全边界文字：

> 来源授权只扩大到账号本身已经免费可见的范围，不改变原站权限判定。浏览器 profile 是部署数据而非代码资产；系统不得记录明文密码、打印 Cookie、把 profile 打包进交付物，或通过并发、翻页和高频调度放大站点负载。

### 5.3 新增“评价口径与可重复测试”章节

每项指标需给出：样本选择、人工金标准、公式、阈值、失败样本保存位置、复测方式。建议增加如下硬门槛：

- 无证据生成的公告事实数为 0。
- 未授权、过期或验证失败不得显示为“授权成功”。
- 单来源故障不会导致其他来源结果丢失。
- “0 条命中”与“覆盖不完整”必须是两个不同状态。
- 页面、API、Word 对同一运行的标题、日期、来源和链接保持一致。
- 敏感配置、浏览器 profile、数据库和 Cookie 不进入 Git 与源码交付 ZIP。

这些门槛适合做发布校验；检索召回率、人工节省时间等依赖真实业务样本的指标，则放入 4 周试点评价。

## 6. Demo 的具体增强建议

### 6.1 叙事原则

Demo 不要从首页菜单逐项浏览。选择一个企业角色和一个真实问题，让屏幕始终回答“下一步业务动作是什么”。建议主角为“企业采购情报专员”，审计同事在结尾承担“证据与合规复核”，这既符合实际分工，也不会虚构其核心研发贡献。

### 6.2 推荐 4 分钟分镜

| 时间 | 画面与操作 | 必须说清的验收点 |
|---|---|---|
| 0:00–0:25 | 一句话问题，展示解析与人工确认 | AI 不直接执行未确认口径；对象是可审计任务，不是聊天答案 |
| 0:25–1:15 | 执行真实多源检索，展开来源漏斗 | 每个来源显示扫描/候选/保留/失败；单源失败不等于全网没有 |
| 1:15–1:55 | 随机打开一条结果与 Word | 现场指认 E 编号、来源、原文、证据片段、附件或“未发现附件” |
| 1:55–2:35 | 展示企业适配、风险、下一步并加入机会 | 判断受证据约束，分数可解释，不承诺中标；动作进入业务工作台 |
| 2:35–3:05 | 展示千里马“已验证”及即时查询 | 说明本人免费账号、服务器 profile、最后验证、查询预算；遮挡账号，不触碰付费详情 |
| 3:05–3:35 | 创建订阅，展示历史仅新增和逐目标状态 | 公开来源进入定时任务；来源覆盖与渠道送达分开；失败可重试/入死信 |
| 3:35–4:00 | 展示评价矩阵与 Linux/CI 证据 | 只报已有测试事实；业务数字明确为 4 周试点目标 |

### 6.3 Demo 口播建议

开场：

> 企业真正缺的不是另一张公告列表，而是一条能说明“为什么找到、为什么保留、接下来谁来做什么”的情报工作流。下面用一个真实问题，现场走完检索、证据、判断、跟进和增量交付。

证据页：

> 这条结果的标题、日期、来源和链接来自固定运行证据，核心内容可以回到 E 编号和原文片段；原站有附件才展示附件，没有就明确写缺失。模型不能补写采购人、编号或金额。

登录态页：

> 这是用户本人免费账号的已验证会话。首次登录在服务器的可见浏览器完成，后台只复用同一持久 profile，在账号原本可见范围内做一次有界列表检索；Cookie 不导出，过期就降级并要求复验。会员监控默认关闭，必须有书面授权或官方 API 记录编号才可启用。

结尾：

> 我们用五层评价矩阵验收系统：来源是否真实、事实能否追溯、筛选是否可复核、工程能否长期运行、业务是否真正节省时间。前四层已有代码和运行证据；效率与转化将在 4 周客户试点中按同口径基线验证。

### 6.4 现场备份方案

- 真实网络波动时，先展示本轮失败诊断，再打开同一版本预先生成的真实运行记录；必须明确这是“历史真实记录”，不能伪装为刚刚在线抓取。
- 登录会话失效时直接展示失效状态和重新登录流程，不临时手工注入 Cookie。
- 准备一条正向结果和一条零结果任务。零结果重点展示淘汰原因、来源缺口和安全放宽建议。
- 录屏前遮挡账号、手机号、Cookie、Token、Webhook、服务器公网地址和浏览器 profile 路径中的个人信息。
- Word、网页、口播使用同一个运行 ID 和同一批证据，避免现场字段不一致。

## 7. 文档统一用词与禁止表述

### 推荐统一用词

- “用户本人免费账号的已验证持久浏览器会话”
- “账号原本可见范围内的受限复用”
- “默认即时、单主题、页数/结果/冷却/每日预算”

- “绕过登录”“绕过会员”“获取全站数据”“无限采集”
- “100% 准确”“覆盖全部招标信息”“零漏报”
- “已有移动 App”（除非真正交付并测试原生应用）
- “已有企业客户节省 XX% 时间”（除非有可审计试点数据）
- “自动替企业作出投标决定”
- “审计同事主导核心研发”（若事实只是参与合规与材料复核）
- “千里马会员内容可用于定时批量抓取”
